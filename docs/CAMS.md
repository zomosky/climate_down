# CAMS 全球大气成分预报

独立生产源为 `ec_cams`，ADS 产品为 `cams-global-atmospheric-composition-forecasts`。
这是 ADS 提交、排队、提取、传输子流程，不使用开放数据的逐时效 byte-range 下载入口。
下游仍使用标准的每起报 manifest → `climate_restore` → `climate_zrread`。

## 固定数据契约

沿用已完成14次起报验收的52个光伏/风电相关变量。完整变量表在
`src/climate_download/cams/catalogue.py`，包含 ADS 名称、参数ID、单位、层次及原生步长。
中国区域为55–15°N、70–140°E，ADS原生0.4°网格为176×100。

每次00/12 UTC起报保留完整0–120小时：45个变量各121个逐小时时效；
过去3小时10米阵风、850hPa的位势/温度/U风/V风/比湿/相对湿度各41个3小时时效。
合计5732条GRIB消息。三个请求分别为5445、41、246字段，均低于本次核实的10000字段限制。
3小时变量在其余80个逐小时时刻的原始Zarr缺测会明确保留，不用插值冒充原始数据。

累积能量和降水保持原值，仅在切片时规范统计属性；原始stepType和累计起点另有属性留存。
读取层按实际时间间隔差分，h0无左区间的通量缺测保留。AOD保持瞬时值，阵风按区间极值处理。
`ssrd_accum`和`ssrdc_accum`沿用已验收的15分钟太阳辐射处理；长波不走太阳辐射曲线。

## 下载与恢复

```bash
uv sync --extra cams --extra s2s --inexact
uv run --extra cams climate_download cams --config config/jobs/cams_operational.yaml \
  --date 20261021 --cycle 0 --preflight-only
uv run --extra cams climate_download cams --config config/jobs/cams_operational.yaml \
  --date 20261021 --cycle 0
```

凭据只从配置中的文件读取，不写入配置、日志或命令参数。账号应自行在ADS站点接受条款。
程序只读核实站点访问、CC-BY条款、原生时效和成本，不代替用户接受条款。
00 UTC归属zmy，12 UTC归属zhangzomo；第三账号zomo不参与。一个账号只有一个下载worker。

状态在 `<root>/ec_cams/<date>/<cycle>z/.cams/<group>/state.json`。
请求ID、账号、请求摘要及原始分片固定关联；常规重复调用恢复同一个请求，不自动取消。
仅明确启用并在首次提交时固定策略的新请求，可按下述MARS计数异常规则追加一次原参数请求。
提交前先持久化意图；提交响应不确定或提交中崩溃会停止自动重提，需只读核对ADS原请求ID后恢复。
`remote_failed`和`validation_failed`保留失败证据，必须定位后处理，不能删除状态以绕过失败。
定时扫描会单独报告这些需检查的起报，并继续后续起报；不会自动重提原失败请求。
仍在排队、传输或持有账号锁的起报继续按原请求恢复，不把整个缺口批量提交到ADS。

下载的完整性检查覆盖全部参数、原生时效、起报、UTC有效时刻、层次、单位、网格和统计窗口。
先验证原始分组，再原样拆成121份逐时效GRIB，保存逐消息及逐文件SHA256。
三个分组齐全且总计5732条消息后，最后原子发布标准 `*.manifest.json`。
未完成的下载不会发布ready信号。完整重复运行不改manifest时间戳。

## 241定时运行

`deploy/cams_run.py`部署为 `/home/zhangmingyu/operation/cams_run.py`。
每5分钟分别驱动00/12 UTC，宿主机和容器内都有锁；每10分钟单worker扫描CAMS完整manifest。
原有其他源的下载、切片和资源配置保持独立。

当前配置 `publish_lag_hours=10`：00 UTC起报在北京时间当天18:00起进入下载候选，
12 UTC起报在北京时间次日06:00起进入候选。定时任务在随后第一个5分钟检查点尝试下载；
完整原生字段尚未发布时顺延，已有请求继续使用原ID。这个时刻是开始尝试时间，完成还需ADS排队、传输和切片。

`first_init="2026102100"`为本次部署下限，`lookback_days=1`仅恢复近期已发布起报。
已经保存请求ID的未完成起报会优先按原ID恢复；追加请求仅遵循首次固定的MARS计数异常恢复规则。
生产下限之前的历史请求由其独立回补worker续传，正常cron扫描不会接管或阻塞这些请求。
这不是全年回补入口；CLI单次`--date`也不接受日期区间。
已明确授权的有限缺口可在对应起报目录保存 `cams.catchup.json`，记录 `date`、`cycle`、
`authorized_at` 及恢复原因。定时扫描只接纳生产下限之后、已到发布时间的标记，
即使近期窗口移动仍继续补齐；正式manifest发布后保留标记作审计，但不再额外调度该旧起报。
历史回补与实时任务共用优先级判定；终止失败不再造成历史任务无限等待，提交结果不确定仍需核对原订单。
官方00/12 UTC发布约为10/22 UTC，ADS排队、传输及切片延迟另计，不保证+10h已经落盘。
官方时刻依据：[ECMWF dissemination schedule](https://confluence.ecmwf.int/pages/viewpage.action?navigatingVersions=true&pageId=738034858)。

### MARS字段计数异常恢复

2026年10月22、23、26日共6条失败均为ADS生成的MARS请求报`-43`，
包含`Expected …, got …`。标准ADS请求本身没有`number`或`expect`键；
日志中的`number=all`由上游生成。同日期、同账号、同参数重提后成功，
支持间歇性上游提取异常的判断，不能据此认定某个气象变量无效或声称修复了ADS内部实现。
官方对计数错误及`all`的说明见[ECMWF Retrieve](https://confluence.ecmwf.int/spaces/UDOC/pages/45751811/Retrieve)。

生产配置开启`mars_count_retry_limit=1`和`mars_count_retry_delay_seconds=1800`；
配置模型默认关闭，独立历史冻结任务不会被追溯启用。
策略在新请求第一次提交前固定，已有订单不因修改配置而追加新的重试授权。
检测在日志截短之前进行，完整脱敏错误、原失败state/request和SHA256保存在
`.cams/<group>/failures/<request-id-hash>/`。

仅在原订单明确`failed`、错误确为MARS -43且字段计数不一致、远端与本地参数完全一致、
没有任何原始/分片字节时进入`retry_wait`。30分钟后重新核对原订单、账号无active订单、
条款/原生可用性/成本及归档校验和，再最多追加一次完全相同参数的请求。
新旧ID与归档固定关联，提交意图和已用次数先落盘；响应不确定时继续停止自动提交。
账号仍在处理其他订单或元数据暂不可读时继续等待，不消耗重试预算。
再次失败、参数或校验异常、访问拒绝等情况保留待查，不继续自动追加。
提交结果不确定且缺少ID的起报在近期窗口移动后仍保留调度可见性。
此恢复保持全部52变量、5732消息和原生时效检查，不能替代上游稳定性保证。

宿主机运行记录为 `operation/cams/run-00.json`、`run-12.json`及`runs.jsonl`，包含真实触发方式和时间。
账号组状态保存ADS排队/提取时间戳、传输尝试字节数和时长；未完成请求只报告已等待时间。

## 按周向前回补（2026-10-27授权）

新增有限历史队列：2026-01-01至2026-09-21，共528次00/12 UTC起报，
从9月15日至21日开始，每次向前推进连续7天，共38批；最后一批为1月1日至5日。
已经存在的9月22日之后的数据由原月度/实时流程负责，不重新创建历史请求。
52变量、5732条消息、0–120小时原生时效及原始缺测语义保持一致。

`cams.backfill`复用正式下载器及账号/起报锁，每次只推进一个起报的有限下载片段。
每个账号最多处理一个历史起报；实时出现待处理起报时，历史任务让出账号。
历史下载配置仅在内存中使用2026年1月1日下限，原实时配置仍保留2026年10月21日下限。
失败、验证不通过及提交结果不确定的原记录保留；仅首次提交时启用MARS计数异常恢复策略的新请求可按上述规则追加一次，其他失败保留待查。
同一批的其他起报可以继续，但该批未全部通过验收就不能进入前一批。

宿主机入口为`deploy/cams_backfill.py`，分别运行`--cycle 0`、`--cycle 12`和`--accept`。
部署清单固定计划SHA256，账号凭据继续从已有配置文件读取。
每批必须先有全部manifest和完整Zarr，再按起报执行全部52变量的原始字节/SHA、
GRIB至Zarr逐值、区域/站点查询、原生及15分钟时刻、通量与原始缺测检查，
并保存NetCDF导出、回读和SHA256。匹配的IFS起报存在时额外核对多源结果；
不存在时明确记录缺失，不以另一数据源缺失阻断CAMS自身验收，也不声称多源通过。

每批最终`assessment.json`记录全部起报及验收文件摘要。
只有该记录完整且摘要一致时，下载器才打开前一周。
宿主机`status.json`、每账号运行记录和每批工件可用于区分“正在下载”“等待实时”
“等待切片”“正在验收”和“完成”；排队或存在manifest不代表整批验收完成。
